# Astra 管理治理裁定

## 0. 裁定范围与证据边界

这是对协调行为、工作结构和治理目标的裁定，不是对编译器实现本身的技术评审。结论依据：

- `RECORD-FOR-ASTRA.md` 的可核实产出、失败和自陈；
- `architecture-work-plan.md` 的 P00–P12 闸门、角色和验收规则；
- `docs/architecture/` 的 A–F 职责分类、目的地契约、分层验证；
- `PROGRAMME-REVIEW.md` 的 P12 汇总。

我没有重新运行构建、测试、CI 或 Git 历史。因此，记录中标为“实测”“进入版本控制”“今天提交”的事实，在本裁定中是**记录所称事实**，不是我重新核验的事实。记录本身还有以下不能直接作为可靠管理指标的地方：

1. 标题/叙述说“今天 6 个提交”，表格实际列出 5 个提交；提交数需要以固定 HEAD 的 `git log` 和范围定义复核。
2. “125 份报告”的总数与分类合计相符，但报告数量不等于交付数量；其中 xcheck、record、audit、咨询都不是架构改进交付。
3. “某修复已完成”与“已进入协调主线、已在同一候选上通过验收”被混用。P12 资料明确显示至少 W1 存在“席位确认”但未证明已经进入冻结候选。
4. `-typecheck`、局部生成、scratch 工作树上的成功不能证明构建、运行、CI 收集或固定版本 Tiqian 回归成功。
5. P12 资料也指出若干更深的未建立事实：P09 没有被完整执行，基线债务没有有限清单，某些 scratch 修复与主线的对应关系没有逐项确认。

因此，本裁定不把“报告很多”当成“完成很多”，也不把“闸门未打勾”当成“完全没有任何有价值产出”。正确的管理单位是：**一个冻结候选、一个明确责任、一个进入版本控制的变更、以及与该候选绑定的分层证据**。

## 1. 总裁定

当前不是“缺少调查”，而是**缺少受控交付系统**。协调者把调查、复核、记录和咨询扩张成了工作本身，却没有稳定地把它们压缩成：

> 选定闸门 → 指定唯一执行责任 → 在一条可集成线上交付 → 独立复核该交付 → 用固定输入运行所需证据 → 更新闸门和下一步。

最致命的不是某一次误判，而是**没有把协调权用于容量、顺序、集成和停止控制**。这使得其他五项失败相互放大：席位空置，执行不足；副本分叉，无法集成；`typecheck` 过弱，回归漏检；报告增殖，真实状态不清；标准已明确却反复请求裁定。

立即生效的总规则：

- 只允许一个当前 P08 候选；候选冻结后不得混入未记录的变更。
- 未指向当前闸门或当前候选的调查、咨询、重写、审计，默认暂停。
- 每个执行席位必须有唯一责任、基线、允许文件、完成命令和交付提交。
- 每个复核席位只复核已存在的执行产出；不复核复核报告，不产生“核验的核验”。
- 任何“完成”必须回答：改了什么、在哪个版本控制提交、哪条命令观察到什么、哪些层仍未验证、下一闸门是什么。
- 标准已作出决定且没有真实技术分歧时，不问用户二选一；直接执行并记录约束。

## 2. 七个席位的工作结构

“执行:核验”建议为 **5:2**，必要时可短暂为 4:2 留一个集成/故障处理席位；不得把 7 席固定成 1 个执行、6 个复核。核验只能在对应执行产出后派出，且**不得核验核验**。协调者本人不应占用一个长期执行席位来制造第八种状态；他负责调度、集成、验收和升级。

### 席位 1：当前提交回归修复（执行）

- **职责**：修复已提交的 lambda/blockExpression 回归；只处理当前已提交缺陷，不顺手重构 A–F。
- **产出形态**：直接基于当前协调主线的可集成提交；附最小复现、修复前失败、修复后成功、受影响文件清单。
- **完成定义**：主线提交存在；完整构建路径（不能只用 `-typecheck`）通过；最小回归通过；原有 W1/lambda 相关行为未被破坏；执行记录写明未验证项。
- **不该做**：不新开互相分叉的长期副本；不写架构总报告；不把“补丁在工作树里”报为完成。

### 席位 2：测试收集与 CI（执行）

- **职责**：修复 `bun run test`/焦点夹具的收集链路，并把必要的测试接入例行 CI；先处理 stale expectation、驱动短路和 gap fixture 的收集缺口。
- **产出形态**：一个提交加收集证明：列出预期测试集合、实际集合、失败集合、CI 入口和故意破坏后的失败证明。
- **完成定义**：正常运行确实执行指定夹具；删除/破坏保护性断言时命令失败；CI 调用该入口；基线红项被单独命名，不能以“没有计数”绕过标准。
- **不该做**：不扩展成通用 provenance/诊断平台；不把收集器能启动等同于候选通过；不改变验收标准来消除红项。

### 席位 3：P08 条件 3 / 目的地契约（执行）

- **职责**：完成 `switchExpression` 等值生产路径的显式目的地传递，处理 nil-merge/refused cell 等已知契约缺口；只在席位 1 的回归修复稳定后合并。
- **产出形态**：一个窄范围提交，配契约对照表（生产者、目的地属主、消费者）和正/反例。
- **完成定义**：实际目的地由包围组合提供；目标错误后端或错误目的地能使测试失败；L1/L2/L3/L4 所需层次分别记录；无无关生成树变化，或对变化有逐项解释。
- **不该做**：不引入“万能 IR”；不因输出未变化而制造差异；不把静态未观察到差异写成“已证明不存在”。

### 席位 4：P08 行为/夹具执行（执行）

- **职责**：维护 P08 选定机制的行为矩阵、固定输入和 oracle；负责判别性测试、完整构建和运行证据。
- **产出形态**：固定候选的不可变证据目录，含输入身份、命令、退出码、原始输出、预期集合和失败分类。
- **完成定义**：候选冻结后运行；生成、类型/语法、完整构建、运行和判别性负控分别有证据；不得用一张“通过”概括不同层次。
- **不该做**：不重复已有调查；不把 scratch 结果拼成一个从未实际运行过的“组合结果”；不修改测试后隐瞒失败。

### 席位 5：集成与 P08/P09 记录执行（执行/集成）

- **职责**：维护唯一候选主线，合并已接受提交；同时先完成 P09 基线预算决定所需的有限事实，再准备固定 Boring/Tiqian 对。
- **产出形态**：主线提交序列、候选冻结记录、P09 预算/负责人/恢复清单和固定输入清单。
- **完成定义**：所有进入候选的变更都有提交；候选 hash、Tiqian revision、工具链、配置和工作树状态可复现；P09 只有在预算负责人和恢复方案明确后才启动重型运行。
- **不该做**：不把多个副本手工拼接；不同时启动多个重型全矩阵；不把准备、清单、manifest 命名为回归已执行。

### 席位 6：P08 实现独立复核（核验）

- **职责**：在席位 1/3/4 交付并冻结后，独立检查事实交接、代码范围、完整构建和警告。
- **产出形态**：针对同一候选 revision 的接受/拒绝清单；每项结论链接到代码或原始证据。
- **完成定义**：明确接受或拒绝 P08，不写模糊“基本完成”；发现问题返回具体执行席位；不复核自己的复核过程。
- **不该做**：不重写 RECORD 作为工作成果；不审计另一个审计者的措辞；不替未运行的测试作正面结论。

### 席位 7：计划/闸门独立核验（核验）

- **职责**：核对 P08、P09、P10、P12 的门槛、提交、证据和状态是否一致；检查是否发生越权关闭或把准备工作冒充执行。
- **产出形态**：一页 gate ledger：每个判据为 PASS/FAIL/NOT ESTABLISHED，给出证据位置和阻塞责任。
- **完成定义**：能由另一人用 ledger 重建状态；没有新的技术调查；P12 明确保持打开，直到五项完成条件都有证据。
- **不该做**：不核验席位 6 的“核验质量”；不增加新门槛；不把咨询意见当成执行证据。

### 协调者本人的职责边界

协调者必须做：确定当前闸门和顺序、分配席位、保持单一候选、集成提交、拒绝越界工作、做最终验收、更新计划和派发下一轮。协调者可以执行一个短的必要命令以确认既有证据，但不应长期亲自承担全部修复。

协调者不得做：用连续小轮次替代交付；在多个副本里重复同一修复；为增加报告数而派 xcheck；在标准已明确时询问用户；把自己的记录修改、咨询、复核和调查累计成“完成度”。

## 3. 交付物、提交和板行验收

是的，修复原则上应直接落在**一条受控集成线上**，而不是每次新开从同一基点分叉的长期副本。隔离工作树可以用于执行，但只能有一个明确集成者、一个基线、一个合并顺序；修复完成后必须尽快回到主线并清理或明确废弃副本。

板行验收判据必须包含“进入版本控制”，更准确地说应包含四件事：

1. 变更已进入指定分支/提交，提交 ID 可定位；
2. 验收命令针对这个提交或明确记录的候选字节运行；
3. 证据保存在规定目录，包含原始输出和输入身份；
4. 仍未满足的层次和闸门没有被隐藏。

“工作树有补丁”是执行完成候选，不是交付完成；“报告写了通过”更不是交付完成。

## 4. 什么才算“架构治理推进了一轮”

一轮的最小闭环不是文档、提交或勾选三者之一，而是：

> **一个有闸门归属的架构问题，被指定给责任人；完成一项可审查的代码/测试/文档变更；该变更进入版本控制；在固定候选上获得相称的独立证据；更新唯一状态记录。**

三类产物的地位不同：

- **文档**：定义契约、责任、验收方法；只有在改变后续行为并经过例证时才是治理进展。
- **提交**：证明有可追踪的交付；提交本身不证明正确，也不自动关闭闸门。
- **闸门打勾**：是该闸门全部条件已满足的管理声明；不能以局部提交代替。

所以每轮判据应为：先有进入版本控制的变更和分层验证，再根据闸门全部条件决定是否打勾。对于当前项目，“架构治理推进一轮”至少应产出一个真正改善 A–F 契约或验证机制的提交，并且该提交经过相关行为、构建和回归证据；纯 scratch 报告、重复咨询、记录重写不算一轮。

## 5. 五条并行线的顺序与停工裁定

先冻结范围：**A–F 重组停下，P09 修订配对的执行准备停下，所有泛化调查、重复审计、重复咨询和报告重写停下。** A–F 是责任分类，不是当前必须大规模重构代码的任务；P09 不能在候选和基线预算没有稳定前继续制造准备物。

当前顺序如下：

1. **先处理已提交回归**：这是现有主线的紧急完整性问题。不能在有已知回归时继续叠加候选。
2. **并行修复收集基础设施**：它与回归修复文件范围不同，可以同时做，但必须作为独立提交；完成后运行真实收集并保留基线失败，不得绕过标准。
3. **再完成条件 3/目的地修复和其 refused-cell 决策**：依赖前两项的可运行、可收集验证面；随后冻结 P08 候选。
4. **P08 双重独立复核与行为/实现接受**：不是单独一份报告，而是对同一冻结候选的两个独立结论。拒绝则回到对应执行席位，不重开无边界调查。
5. **P09 修订配对**：先作基线预算/负责人/恢复方案的明确管理决定，再选定一个 Boring revision 与固定 Tiqian revision，执行完整矩阵。准备材料不计为 P09 运行。
6. **P10 反思和 P12**：在 P08/P09 证据齐全后分类失败、修订规范、做后续指导评估，并决定是否打勾。

关于“停下来”的明确答案：

- **收集修复：继续，但限于让指定测试真实进入例行命令和 CI。**
- **回归修复：继续，最高优先级。**
- **条件 3：继续，但排在回归稳定和收集可运行之后。**
- **A–F 代码重组：停止。** 保留分类文档；只有当前 P08/P09 的明确消费者才可按分类做窄修复。
- **P09 修订配对：停止泛化准备；先完成预算和候选冻结，之后只做一次固定配对的实际运行。**

## 6. 六项管理失败中最致命的一项

最致命的是 **3.1：把核验权重放大到超过执行**；但更根本的表述是：协调者没有建立“执行—集成—验收”的单一流水线，也没有把席位容量绑定到可交付目标上。

为什么它最致命：核验只能证明已有产出；当执行不足、席位空置、交付不进主线时，增加 xcheck 只会增加元数据，不会增加系统能力。它还掩盖了 3.2 的席位空置、3.3 的副本分叉和 3.5 的沉溺细节。

先改的不是报告模板，而是**调度纪律**：

1. 每轮先列 7 席实际占用和每席提交目标；空席必须补具体执行任务或明确说明依赖。
2. 任何核验任务必须引用已存在的执行提交和候选 ID；禁止核验报告。
3. 每三个调度周期必须至少有一个进入版本控制的交付，否则暂停新调查并由协调者重新分配。
4. 标准已决定的事项直接执行；只有语义或真实技术分歧才升级用户。

自我诊断还遗漏了一个根本问题：**没有“停止/取消”治理**。协调者看见新问题就增派任务，却没有关闭无关任务、淘汰过期候选、回收席位和清理工作树。另一个遗漏是**没有单一真相源**：RECORD、board、scratch 报告、多个工作树和闸门文件之间没有强制同步规则。

## 7. 是否继续让该协调者协调

不应立即完全撤换，但也不应让其以现有方式继续担任唯一协调者。建议实行**受限协调试用**：

- 该协调者保留架构设计、任务简报、候选集成和闸门记录职责；
- 席位 7 的独立 gate steward 暂时拥有“拒绝关闭闸门、拒绝新增越界任务”的否决权；
- 两轮内必须证明：7 席有明确占用、至少 5:2 执行/核验比例、每个执行任务有提交、无核验的核验、只有一个候选主线；
- 若两轮仍以报告增长而非提交和闸门证据增长，立即改为“执行 Agent/架构记录员”，把协调、分配和停止权交给另一 Agent。

这不是惩罚，而是把“能发现问题”和“能治理交付”分开。当前记录证明前者较强，后者尚未达到独立协调整个计划的要求。

## 8. 明确完成定义（Definition of Done）

一个执行任务只有同时满足以下条件才可标记 done：

1. 有唯一任务 ID、闸门归属、基线 revision、允许文件和依赖；
2. 有进入版本控制的提交；
3. 有修复前失败和修复后结果，且命令确实观察了目标性质；
4. 使用适当验证层：生成、类型、完整构建、运行、判别性负控按任务需要分别记录；不能以 `-typecheck` 代替完整构建；
5. 有独立复核，复核的是同一提交/候选，而不是报告文字；
6. 任何失败、基线红项、未执行项和不确定性都显式列出；
7. 更新唯一状态记录，并明确下一闸门或阻塞责任。

一个闸门只有在其计划列出的全部条件满足时才可打勾。当前 P12 必须保持未关闭：P12 记录的判据 3、4 不成立，且 P08/P09 仍有未接受证据。没有任何席位可以用“报告已写”“修复在 scratch”“局部测试通过”替代这一裁定。

## 9. 对用户批评的逐条回应

- **“五百多轮实际产出是什么？”** 记录能支持的答案是：少量已提交代码、三份架构文档和若干局部验证；不是五百轮等价的架构改进。提交数和主线归属仍应按 Git 复核。
- **“124/125 份报告是什么？”** 主要是交叉核验、修订记录、调查和咨询，只有一部分包含修复；它们是证据碎片，不是架构方案。以后报告只作为交付记录，不作为工作目标。
- **“席位满吗、职责推进吗？”** 先前 7 席只用 1 席是明确管理失败。新结构要求 5 个执行、2 个独立核验，并每轮记录占用和提交目标。
- **“谁调查谁执行？”** 调查由席位 4/5 在当前闸门范围内完成；执行由席位 1–5 完成；席位 6–7 只做独立核验和闸门核对；协调者集成和决策，不制造核验循环。
- **“什么叫待我裁定？”** 已被标准和计划决定的事项不再上问。只有会改变语义、验收契约、资源预算或候选范围的真实技术决策才升级；其余按既有标准执行并记录。

**最终治理目标：少写一份报告，多交付一个可追踪的候选；少开一个副本，多完成一次闭环；不以工作量证明治理，而以提交、独立证据和正确闸门状态证明治理。**
