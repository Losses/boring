# Crypto spec 01: SHA-256 and SHA-512

## API

The portable APIs accept bytes and return bytes. Text is not part of the
hash contract.

```haxe
Sha256.make(data:Bytes):Bytes;
Sha512.make(data:Bytes):Bytes;

var hash = new Sha256();
hash.update(data);
var digest = hash.digest();
```

The incremental and one-shot forms have identical results. `digest` does not
change the observable digest on repeated calls unless a later `update` is
performed according to the class contract.

## Implementation

The source implementations are portable Haxe code. PHP and Java branches are
not part of this capability. No external crypto package is required by any
target. SHA-256 uses 32-bit `Int` operations. SHA-512 uses `haxe.Int64`
for every state word, schedule word, round constant, and intermediate value.
The compiler treats Int64 as a general platform capability and does not special-case either hash module.

Target output uses the minimum representation that preserves the contract:
fixed byte storage for blocks and digests, borrowed byte input where the
target has ownership, and owned byte output. A target-native operation is
emitted directly; runtime calls are limited to host boundaries and missing
language operations.

## Padding and length

SHA-256 uses a 64-byte block and a 64-bit encoded bit length. SHA-512 uses a
128-byte block and a 128-bit encoded bit length. The length counter is not a
`Float`, is not affected by `float-precision`, and must not silently narrow.
The implementation either carries the full counter or rejects an input before
processing when the configured counter domain would overflow.

## JavaScript hosts

The TypeScript target has one portable synchronous implementation. Node, Bun,
and Deno host entries may select a synchronous host-native bridge when the
entry provides one; the Int64 capability remains available in those targets.
Browser output must not statically import a Node-only module and uses the
portable synchronous implementation. Web Crypto asynchronous APIs are out
of scope because the subset has no async model.

## Bytes ownership

Haxe source uses `Bytes`. The target ABI assigns the operation's ownership:
Rust inputs lower to `&[u8]`, mutable internal blocks to local mutable byte
storage, and returned digests to `Vec<u8>`. Other targets use their native
byte sequence and array types. This ABI rule does not require public
Haxe `ReadOnlyBytes` or `WritableBytes` types.

`BytesBuffer` remains the dynamic sink. Hash blocks and final digests use
fixed-size buffers whenever the target can express the size directly.

## Compiler discipline

New lowering is implemented with typed AST and structured Reflaxe data. The
compiler must not recognize or rewrite these features with string searches,
regular expressions, or ad hoc target-source construction. Existing fixed
runtime source is permitted only for independent runtime declarations and
host bridges.

## Tests

Every supported target compiles and executes the same vectors. Tests cover
empty input, `abc`, each padding boundary, input spanning more than one block, incremental
chunking, and one-shot equality. Results compare digest bytes exactly. The
SHA suite also runs the independent Int64 capability vectors. Generated
sources are compiled by the target compiler; text-only snapshots are not
sufficient evidence.
