# The number on the last line is the whole-repo hit count that
# `bun tools/doc-style/check.ts` reports on the current mainline. check:docs
# has a standing red state (TCN-213 "check:docs is red by design"): the word
# list and sentence patterns flag a large body of existing prose as candidates,

# The pre-commit hook (tools/git-hooks/pre-commit) reads this number and only
# refuses a commit when the measured count EXCEEDS it - that is, when the
# commit introduces a new doc-style candidate. A count at or below the
# baseline passes and the hook reports the standing red state truthfully.
#

# longer scans the subtree of any directory that carries a SHA256SUMS manifest.
# Such a directory holds byte-pinned copies of build artifacts, so a hit inside
# it cannot be repaired without breaking the manifest, and check.ts already
# excluded the out/ directory those copies came from. The 2203 pinned for
# cfec9666 was measured WITH the mirrors in scope, so the two numbers are not
# comparable: the drop to 1569 records a scope correction, and no hit was
# repaired to earn it. Most of the 1627 that left the count were the 170 files
# H9 ingested (954 hits) plus the mirrors already in the tree.
#
# This file is a fact pin, not a sign-off: recording a number here means "the
# tree already reads N and a deviation must be visible", not "every one of N
# hits was reviewed and accepted". Refresh it deliberately:
#   - LOWER it when hits are fixed, to lock in the improvement.
#   - RAISE it only after the new hits have been reviewed by a human, never as
#     a side effect of some unrelated commit (same rule as TCN-24 for the
#     warning-gate baselines).
#   - After a check.ts word-list growth (new banned term or pattern), the
#     measured count jumps without any prose change; re-measure and refresh
#     here in the same commit that changes the word list.
#   - After a change to what check.ts SCANS, re-measure and refresh here in the
#     same commit, and say in the commit message that the new number is not
